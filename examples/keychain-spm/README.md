# Keychain SPM — Swift Package Manager + `@objc` shim for kivy-ios 3.0

This example shows how a Kivy app declares a **Swift Package Manager** (SPM)
dependency in `pyproject.toml`, has `toolchain lock` pin it, and then calls it
from Python. The package it uses —
[KeychainAccess](https://github.com/kishikawakatsumi/KeychainAccess) — stores a
secret in the iOS **Keychain**, secure on-device storage that Python has no
native access to on iOS.

KeychainAccess is *pure Swift* (throwing functions and subscripts), so pyobjus
cannot call it directly. The example therefore ships a tiny **local shim
package** that re-exports the calls we need behind an `@objc` class.

## How the pieces fit together

```
pyproject.toml ── declares two SPM packages ──┐
                                               │
  KeychainAccess  (remote)  ── pinned by `toolchain lock` ──> pylock.ios.toml
        ▲                                                     Package.resolved
        │ depends on
  KeychainBridge  (local, swift-shims/)  ── @objc class pyobjus can reach
        ▲
        │ autoclass("KeychainBridge")
   src/main.py  (Kivy + pyobjus)
```

| Path | Purpose |
|------|---------|
| `pyproject.toml` | App config + the two `[tool.kivy.ios.native.swift_packages]` entries |
| `swift-shims/Package.swift` | Local SPM package; depends on KeychainAccess, builds a **dynamic** `KeychainBridge` framework |
| `swift-shims/Sources/KeychainBridge/KeychainBridge.swift` | `@objc(KeychainBridge)` wrapper: `storeString:forKey:`, `stringForKey:`, `deleteKey:` |
| `src/main.py` | Kivy UI; calls the shim via pyobjus, with an in-memory desktop fallback |
| `../wheels/` | Shared locally built Kivy + pyobjus iOS wheels (gitignored `.whl` blobs) |
| `pylock.ios.toml` | Generated by `toolchain lock` (pins KeychainAccess to a commit) |
| `keychain-spm-ios/` | Generated Xcode tree (gitignored; recreated by `toolchain build`) |

### Why a shim, and why a *remote* + *local* pair

- **KeychainAccess (remote, `url` + `requirement`)** — the real dependency.
  Declaring it here is what makes `toolchain lock` resolve it with Xcode's Swift
  toolchain and record the exact commit in `pylock.ios.toml` and the project's
  `Package.resolved`, so the build is reproducible. It is declared with
  `link = false, embed = false` (see below).
- **KeychainBridge (local, `path = "swift-shims"`)** — the bridge. Its
  `Package.swift` depends on KeychainAccess and the `KeychainBridge.swift` source
  exposes Objective-C-representable signatures (`String`/`Bool`) that pyobjus can
  call by selector. The product is declared `.dynamic` so there is a framework to
  embed. The app links + embeds this one (the defaults).

The app target contains no compiled Swift — pyobjus looks the `KeychainBridge`
class up at runtime — so the shim framework must be **embedded** (present in
`.app/Frameworks`) and loaded at launch.

**Why `link = false, embed = false` on KeychainAccess.** Embedding a dynamic SPM
product copies its entire dynamic dependency closure into the bundle. Because
KeychainBridge depends on KeychainAccess, embedding KeychainBridge already brings
KeychainAccess along. Embedding KeychainAccess *again* (the default) makes Xcode
copy and code-sign the same framework twice — `Unexpected duplicate tasks …
CodeSign … KeychainAccess_…_PackageProduct.framework`. So a remote package that is
only reached *through* a local shim should be declared for pinning only, with
`link`/`embed` turned off; the shim carries it into the bundle. (A remote package
the app links against directly keeps the `link = true, embed = true` defaults.)

## Prerequisites

- macOS with Xcode (including the Swift toolchain — `toolchain doctor` checks
  for it whenever `swift_packages` are declared).
- kivy-ios 3.0 installed from this repo (`pip install -e ".[dev]"`).
- Kivy + pyobjus `cp315` iOS wheels in [`examples/wheels/`](../wheels/). Build
  them once from the repo root (see
  [hello-kivy → "Build iOS wheels locally"](../hello-kivy/README.md#1-build-ios-wheels-locally));
  all native examples share the directory via `find_links = ["../wheels"]`.
- Network access to GitHub the first time you lock, so Xcode can fetch
  KeychainAccess.

## Lock, build, run

```bash
cd examples/keychain-spm
toolchain lock --update
toolchain build --simulator
toolchain run --simulator
```

`toolchain lock` resolves both the Python wheels and the Swift packages: it pins
KeychainAccess by commit into `pylock.ios.toml` (alongside the local shim) and
writes the project's `Package.resolved` on the next build.

You can also open the project in Xcode and press Run:

```bash
toolchain open
```

## Try it

1. Type a value into the field and tap **Save** — it is written to the Keychain
   via `KeychainBridge.storeString:forKey:`.
2. Clear the field (or relaunch the app) and tap **Load** — the value comes back
   from the Keychain, proving it persisted outside the app's own memory.
3. Tap **Delete** to remove it.

The banner at the top reports the active backend. On a device/simulator build it
reads *"iOS Keychain (KeychainAccess via @objc shim)"*; on desktop it falls back
to an in-memory store so you can still exercise the UI.

## Run on desktop first (optional)

It's a standard Kivy app, so you can sanity-check the UI on your Mac before
bundling (in a Python env that has desktop Kivy installed):

```bash
python examples/keychain-spm/src/main.py
```

On desktop the native bridge is absent, so the app uses the in-memory fallback
(the banner says so). The Keychain path only runs on iOS.

## Adapting this for your own Swift package

1. Add the remote package under `[tool.kivy.ios.native.swift_packages]` with a
   `url`, a `requirement` rule (`from`, `exact`, `range`, `up_to_next_minor`,
   `branch`, or `revision`), and its `products`.
2. If the package's API is pure Swift (throws, subscripts, enums with associated
   values, generics, structs…), add a local `path` shim like `swift-shims/` that
   re-exports just the calls you need as `@objc` methods with flat signatures.
   Packages that already expose an Objective-C surface can often be called
   directly and need no shim.
3. When you go through a shim, set `link = false, embed = false` on the remote
   package — the shim already depends on it and carries it into the bundle, so
   embedding it directly too would cause duplicate-CodeSign build errors. Keep
   the `link`/`embed` defaults only for a remote package the app links against
   directly (no shim).
4. Call the shim from Python with `autoclass("YourBridge")` and the
   underscore-mangled selector names (`storeString:forKey:` →
   `storeString_forKey_`).
