# 02 — `pylock.ios.toml` Schema

**Status:** rfc-v1 (draft)
**Depends on:** [00-overview](00-overview.md), [01-pyproject-kivy-spec](01-pyproject-kivy-spec.md), [03-artifact-distribution](03-artifact-distribution.md)
**Consumed by:** [06-xcode-project-generation](06-xcode-project-generation.md)

`pylock.ios.toml` is the **reproducibility artifact** generated by `toolchain lock` from the user's `pyproject.toml`. It pins the exact Python wheels, the exact `Python.xcframework`, and the exact native `.xcframework` archives a build will use — by URL and SHA-256 — and records the Xcode wiring intent for each native artifact.

The format **conforms to PEP 751** (`pylock.toml` lock file format, Final since March 2025). PEP 751 permits per-tool extension tables at the top level under `[tool.<name>]`; kivy-ios stores iOS-specific bits (Python.xcframework, native xcframeworks, per-wheel source-index provenance) inside `[tool.kivy_ios]`. The standard `[[packages]]` array is PEP 751-shaped and is intended to remain consumable by PEP 751-aware installers; everything kivy-ios needs lives under the tool table, and kivy-ios does not depend on an installer understanding `[tool.kivy_ios]`.

The matching Android lock for the same `pyproject.toml` would be `pylock.android.toml` with a parallel `[tool.kivy_android]` block, owned by p4a/Buildozer.

This spec defines the schema.

## Design principles

- **PEP 751 conformant.** The standard `[[packages]]` section is a valid PEP 751 lock that any PEP 751-aware consumer (pip, uv, pdm, etc.) can *read* without knowing anything about kivy-ios. Selecting and installing the correct iOS wheel slices onto a macOS host is performed by kivy-ios itself (see "Resolution semantics" and the folder-mapping cross-reference), not delegated to a generic installer's lockfile reader — which, as of pip 26.1, treats `-r pylock.toml` as experimental.
- **Pinned by URL and content hash.** Every artifact entry — wheel or xcframework — has a fetchable URL and a SHA-256 the toolchain verifies before use. (PEP 751 mandates this for wheels; we extend the same rule to xcframeworks.)
- **One artifact, multiple slices.** A single `.xcframework` entry covers all iOS slices (device + simulator); a single Python wheel name may have multiple wheel entries — one per platform tag the build targets.
- **Generated, not hand-edited.** Users edit `pyproject.toml`; `toolchain lock` regenerates `pylock.ios.toml`. Hand-editing is technically possible but unsupported.
- **PEP 751 + Kivy schema versions are independent.** PEP 751 has its own `lock-version`; kivy-ios additionally pins `[tool.kivy_ios].schema_version` so we can evolve the iOS-specific extensions without touching upstream's number.

## Filename

`pylock.ios.toml`, sibling to `pyproject.toml`. PEP 751 reserves the `pylock.toml` name for the project's "default" lock and accepts `pylock.<name>.toml` for additional platform/variant locks. iOS pins to `ios`; Android to `android`. This is the same convention PEP 751 uses for any per-platform fork of the dependency graph.

## Top-level structure

```toml
# Required by PEP 751.
lock-version = "1.0"
created-by = "kivy-ios"
requires-python = ">=3.15"
extras = []
dependency-groups = []
default-groups = []

# Standard PEP 751 package entries; readable by any PEP 751-aware installer.
[[packages]]
# Repeatable. Each entry pins one Python package.

# Kivy-iOS extension: Python.xcframework, native xcframeworks, per-wheel
# source-index provenance, source-pyproject hash, and the [tool.kivy] schema version.
[tool.kivy_ios]
```

## Standard PEP 751 fields

These are required at the top level by PEP 751. kivy-ios populates them as follows:

| Field | Type | Set by `toolchain lock` to |
|-------|------|----------------------------|
| `lock-version` | string | `"1.0"` (current PEP 751 spec). kivy-ios refuses to read a `lock-version` major higher than it understands. |
| `created-by` | string | `"kivy-ios"`. |
| `requires-python` | string | Carried verbatim from `pyproject.toml`'s `[project].requires-python`, with a kivy-ios fallback of `">=3.15"` when the user omits it (kivy-ios 3.0 has a Python 3.15 floor). |
| `extras` | array | `[]` for v3.0 — kivy-ios does not currently consume `[project].optional-dependencies`. |
| `dependency-groups` | array | `[]`. |
| `default-groups` | array | `[]`. |

The lock is therefore always installable for the "default" set of the project — which for iOS apps is the whole `[project].dependencies` table.

## `[[packages]]` — Python wheels (PEP 751 standard)

Every Python package the build needs is one `[[packages]]` entry, following PEP 751 verbatim:

```toml
[[packages]]
name = "kivy"
version = "3.0.0"
requires-python = ">=3.10"
dependencies = [
    { name = "packaging" },
]

[[packages.wheels]]
name = "kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
upload-time = "2026-09-01T10:00:00Z"
url = "https://files.pythonhosted.org/packages/<hash>/kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
hashes = { sha256 = "abc123..." }

[[packages.wheels]]
name = "kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphonesimulator.whl"
upload-time = "2026-09-01T10:00:00Z"
url = "https://files.pythonhosted.org/packages/<hash>/kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphonesimulator.whl"
hashes = { sha256 = "def456..." }
```

The PEP 751 fields kivy-ios emits per package:

| PEP 751 field | Required by PEP 751 | kivy-ios use |
|---------------|---------------------|--------------|
| `name` | yes | PyPI distribution name. |
| `version` | yes | Resolved version. |
| `requires-python` | no | Carried from the wheel metadata. |
| `dependencies` | no | Transitive deps — names of other `[[packages]]` entries this depends on (resolution trace). |
| `marker` | no | PEP 508 environment marker if the dep is conditional. |
| `wheels` / `sdist` / `archive` / `vcs` / `directory` | exactly one of these | Always `wheels` for v3.0. The other PEP 751 source types all imply a build step on the consuming machine — `sdist`, `vcs`, and `directory` require compiling, and kivy-ios has no on-mac/on-device compile path — so they are refused. A wheel may still be sourced locally: the individual `[[packages.wheels]]` entry accepts `path` as well as `url` (see below). |

Per-wheel fields (also PEP 751):

| Field | Required | kivy-ios use |
|-------|----------|--------------|
| `name` | yes | Wheel filename — the platform tag is parsed back out of this for Xcode-slice routing (e.g. `ios_13_0_arm64_iphoneos` vs `ios_13_0_arm64_iphonesimulator`). |
| `upload-time` | no | Recorded from PyPI's `upload_time_iso_8601`. |
| `url` *or* `path` | exactly one | `url` is the resolved download URL on PyPI / a supplemental index / any HTTPS host. `path` references a wheel file on the local filesystem — used for a wheel the author built themselves (see "Locally built wheels" below). Per PEP 751, a relative `path` MUST be relative to the location of `pylock.ios.toml` and SHOULD use POSIX-style separators for portability. |
| `hashes` | yes | SHA-256 verified before extraction. Required for `path` wheels too — `toolchain lock` computes it from the file. |
| `size` | no | Optional, helpful for progress bars. |

### Multi-platform wheels

A compiled-extension wheel appears as **multiple `[[packages.wheels]]` entries inside the same `[[packages]]` block** — one per iOS slice `toolchain lock` pins (device arm64, simulator arm64, and simulator x86_64; see "Resolution semantics"). `toolchain build` selects the right entry per Xcode SDK and `--arch` at build time using the platform tag parsed from `wheels.name`.

### Pure-Python wheels

Pure-Python wheels (`requests`, `jinja2`, etc.) have a single wheel entry with the universal `py3-none-any` filename:

```toml
[[packages]]
name = "requests"
version = "2.32.0"

[[packages.wheels]]
name = "requests-2.32.0-py3-none-any.whl"
upload-time = "2025-04-01T00:00:00Z"
url = "https://files.pythonhosted.org/packages/.../requests-2.32.0-py3-none-any.whl"
hashes = { sha256 = "..." }
```

### Locally built wheels (`path`)

An author who cross-builds their own iOS wheel (see [spec 03 §"App-specific native extensions"](03-artifact-distribution.md)) can vendor it into the repo instead of hosting it. The wheel entry then uses `path` instead of `url`:

```toml
[[packages]]
name = "myext"
version = "0.3.0"

[packages.tool.kivy_ios]
direct_requirement = true

[[packages.wheels]]
name = "myext-0.3.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
path = "wheels/myext-0.3.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
hashes = { sha256 = "..." }
```

This is the standard PEP 751 `path` mechanism, not a kivy-ios invention. Two rules, both from PEP 751, keep it reproducible:

- **Relative to the lockfile.** A relative `path` is resolved relative to `pylock.ios.toml`'s location and SHOULD use POSIX separators. Because the artifact and the path both live in the repo, every clone and CI runner resolves it identically — unlike an absolute path, which is machine-specific. `toolchain build` rejects an absolute `path` (or one escaping the project directory) with a diagnostic.
- **Hash-pinned.** `hashes` is still required; `toolchain lock` computes the SHA-256 from the file at lock time and `toolchain build` verifies it before extraction, exactly as for `url` wheels.

A `path` wheel must still be an iOS-tagged wheel (its filename carries the `ios_..._iphoneos` / `iphonesimulator` platform tag); a pure-Python local wheel uses `py3-none-any`. The wheel is *not* compiled by kivy-ios — it must already be built. For wheels shared across projects, prefer a private/supplemental index (`url`) over vendoring.

### Kivy-ios-specific package metadata: `[tool.kivy_ios]` per-package

PEP 751 allows tool-scoped data on each package via a per-package `[packages.tool.<name>]` table. kivy-ios uses this to mark direct vs transitive deps and supplemental-index provenance:

```toml
[[packages]]
name = "numpy"
version = "2.3.0"

[packages.tool.kivy_ios]
direct_requirement = true
source_index = "https://wheels.example.com/simple"

[[packages.wheels]]
name = "numpy-2.3.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
url = "https://wheels.example.com/simple/numpy/numpy-2.3.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
hashes = { sha256 = "..." }
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `direct_requirement` | bool | no (default `false`) | `true` if the package corresponds to an entry in `[project].dependencies`; `false` for transitive deps. |
| `source_index` | string | no | The index URL the wheel was resolved from. Default-omitted means PyPI proper. Recorded for audit purposes — `toolchain doctor` can report which supplemental index supplied each wheel. |

These tool-scoped fields are invisible to other PEP 751 consumers (pip ignores `tool.*` per the spec), so the lock remains installable by stock pip.

## `[tool.kivy_ios]` — top-level extension

Everything iOS-specific that PEP 751 doesn't model lives here:

```toml
[tool.kivy_ios]
schema_version = 1
toolchain_version = "3.0.0"
generated_at = "2026-05-27T00:00:00Z"
pyproject_sha256 = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
tool_kivy_ios_schema_version = 1

[tool.kivy_ios.python_xcframework]
version = "3.15.0"
url = "https://www.python.org/ftp/python/3.15.0/python-3.15.0-iOS-XCframework.tar.gz"
sha256 = "abd43fc362bb6e40a5233a499aa3fa96bf49306ca10b4cbcb27418778e429eb8"

[[tool.kivy_ios.xcframeworks]]
# Repeatable. Each entry pins one native .xcframework artifact.
```

### `[tool.kivy_ios]` scalar fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `schema_version` | integer | yes | This lockfile's `[tool.kivy_ios]` schema version (independent from PEP 751's `lock-version` and from `[tool.kivy.ios].schema_version` in `pyproject.toml`; all three start at 1). |
| `toolchain_version` | string | yes | Version of `kivy-ios` that generated this lock. |
| `generated_at` | string | yes | ISO 8601 UTC timestamp. |
| `pyproject_sha256` | string | yes | SHA-256 of the source `pyproject.toml` at lock time. `toolchain build` recomputes the hash and exits with an error if it doesn't match. See "Drift detection" below. |
| `tool_kivy_ios_schema_version` | integer | yes | Mirrors `[tool.kivy.ios].schema_version` from the source pyproject — lets future `toolchain` versions know which iOS schema produced this lock. Android's `[tool.kivy.android].schema_version` is not recorded here because this is an iOS-only lockfile; the Android equivalent (`pylock.android.toml`) carries its own analogous field. |

### `[tool.kivy_ios.python_xcframework]`

```toml
[tool.kivy_ios.python_xcframework]
version = "3.15.0"
url = "https://www.python.org/ftp/python/3.15.0/python-3.15.0-iOS-XCframework.tar.gz"
sha256 = "abd43fc362bb6e40a5233a499aa3fa96bf49306ca10b4cbcb27418778e429eb8"
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `version` | string | yes | The `Python.xcframework` version pinned for this build. |
| `url` | string | yes | Resolved download URL. `toolchain lock` constructs this from the requested version — `python-<version>-iOS-XCframework.tar.gz` on python.org's release page (the official artifact, available from 3.15.0b1 onward via `python/release-tools#365`). |
| `sha256` | string | yes | SHA-256 verified before use. python.org additionally signs the artifact with Sigstore; `toolchain build` may verify the Sigstore signature in addition to the SHA-256 (future enhancement). |

The `Python.xcframework` is conceptually an artifact, but it's promoted to its own sub-table rather than appearing as another `[[tool.kivy_ios.xcframeworks]]` row because it's mandatory and singular (one Python runtime per build) rather than a repeating dep. See spec 04 §"Consumed from upstream" for the upstream sourcing narrative.

### `[[tool.kivy_ios.xcframeworks]]`

Each entry pins one pure-native `.xcframework` artifact:

```toml
[[tool.kivy_ios.xcframeworks]]
name = "MyAnalyticsSDK"
version = "4.2.0"
url = "https://example.com/sdks/MyAnalyticsSDK-4.2.0-ios.tar.gz"
sha256 = "..."
archive_format = "tar.gz"
slices = ["ios-arm64", "ios-arm64_x86_64-simulator"]
link = true
embed = true
source = "upstream"
```

This array is typically **empty** in the lockfile of a vanilla Kivy app: the kivy iOS wheel bundles every native xcframework it links against (ANGLE, SDL3 family, etc.) inside the wheel itself. Entries appear only when the user's `pyproject.toml` declares additional third-party xcframeworks under `[tool.kivy.ios.native.xcframeworks]`.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Framework name (matches the `[tool.kivy.ios.native.xcframeworks]` key in pyproject). |
| `version` | string | yes | Resolved version. |
| `url` *or* `path` | exactly one | `url` is a fully-qualified download URL. `path` references a local xcframework artifact (archive or unpacked `.xcframework` directory) vendored in the repo — used when the author builds their own framework. Mirroring PEP 751's wheel-`path` rules, a relative `path` MUST be relative to `pylock.ios.toml` and SHOULD use POSIX separators; `toolchain build` rejects absolute paths or paths escaping the project directory. |
| `sha256` | string | yes | SHA-256 of the artifact. Verified before extraction. For a `path` artifact, `toolchain lock` computes it from the file. |
| `slices` | list of string | yes | XCFramework slice identifiers (matching the directory names inside the `.xcframework`). The lockfile records all slices in the upstream artifact; `toolchain build` may use a subset (typically the iOS-only slices). |
| `archive_format` | string | no (default `"zip"`) | Archive container holding the xcframework: `"zip"` or `"tar.gz"`. |
| `archive_member` | string | no | Relative path inside the archive identifying the xcframework directory to copy. When omitted, the runtime auto-detects a single top-level `.xcframework` directory; only set this when an archive contains multiple xcframeworks or sibling files. |
| `privacy_manifest_path` | string | no | Relative path inside the xcframework to a `PrivacyInfo.xcprivacy` file. If present, `toolchain build` validates it exists. |
| `link` | bool | no (default `true`) | Add to the Xcode target's Link Binary With Libraries phase. |
| `embed` | bool | no (default `true`) | Add to the Xcode target's Embed Frameworks phase. |
| `source` | string | no | Provenance hint: `"upstream"`, `"kivy"` (Kivy artifact builder), or a free-form annotation. Informational. |

### Why `link` and `embed` are explicit

Some xcframeworks should be linked but not embedded (e.g. system-provided frameworks that the user references for symbols but Apple already ships). Some should be embedded but not linked (rare; usually a runtime-loaded plugin). Defaulting both to `true` covers the common case; the toml can override per entry.

## Resolution semantics

`toolchain lock` performs the following:

1. Parses `pyproject.toml`. Validates `[project]` (PEP 621), `[tool.kivy]`, and `[tool.kivy.ios]` against their schemas.
2. Fetches the `Python.xcframework` version's metadata from python.org (or a cache) to populate `[tool.kivy_ios.python_xcframework]`.
3. For each entry in `[project].dependencies`:
   - Invokes pip in resolve-only mode with the right iOS platform tags (`--platform`, `--python-version`, `--abi`, `--implementation`, `--only-binary=:all:`, `--dry-run` or equivalent) to identify the exact wheel for each package.
   - **Pins all three iOS slices, host-independent.** For every package that carries a compiled extension, `toolchain lock` resolves and pins a wheel entry for **each** iOS slice the build can target — device `ios_<target>_arm64_iphoneos`, simulator `ios_<target>_arm64_iphonesimulator`, and simulator `ios_<target>_x86_64_iphonesimulator` — regardless of the architecture of the host running `lock`. This keeps the committed lock reproducible across every host/CI permutation (Apple Silicon *and* `macos-15-intel`); `toolchain build` then selects the matching slice per `--device` / `--simulator` / `--arch` at install time (see [spec 05 §"Step 4 — pip platform tag"](05-cli-shape.md)). Pure-Python packages are unaffected — they resolve to a single `py3-none-any` entry. If a compiled package is missing a slice upstream, `lock` fails fast at lock time (clear, host-independent error) rather than letting `build` fail later on one specific runner.
   - Records direct + transitive resolved wheels as `[[packages]]` blocks with their `[[packages.wheels]]` sub-arrays — pinning a `url` for index/hosted wheels, or a repo-relative `path` for a wheel the author has vendored and referenced locally (e.g. via a direct reference or a local wheel directory). `hashes` is computed for both.
   - Marks direct requirements via `[packages.tool.kivy_ios].direct_requirement = true`.
4. For each entry in `[tool.kivy.ios.native.xcframeworks]`. The `source` is always **explicit** — a direct artifact URL or a repo-relative path — with no manifest or registry indirection (see [spec 01 §`[tool.kivy.ios.native.xcframeworks]`](01-pyproject-kivy-spec.md)):
   - If `source` is a **URL**: downloads the artifact directly (zip, tar.gz, or unpacked `.xcframework`), computes its SHA-256, and enumerates its slices (and `privacy_manifest_path`, if present) by reading the artifact itself.
   - If `source` is a **repo-relative path**: reads the vendored artifact the same way to compute its SHA-256 and enumerate its slices; no network fetch.
   - Records as `[[tool.kivy_ios.xcframeworks]]` (with `url` or `path` accordingly).
5. Writes `pylock.ios.toml` atomically (write to tempfile, fsync, rename).

The order of `[[packages]]` and `[[tool.kivy_ios.xcframeworks]]` entries within the file is **deterministic** (sorted by `name`, then `version`, then platform tag for wheels) so diffs across `toolchain lock` runs only show real changes.

## Drift detection

`toolchain build` recomputes `pyproject_sha256` from the current `pyproject.toml`. If it doesn't match `[tool.kivy_ios].pyproject_sha256` in the lock, `toolchain build` exits with:

```
Error: pyproject.toml has changed since pylock.ios.toml was generated.
  Run: toolchain lock
  Or:  toolchain build --no-verify-lock   (not recommended)
```

The `--no-verify-lock` escape hatch exists for CI scenarios where lock and pyproject may be regenerated in the same job.

## Hash verification

Every artifact download is verified against its declared `sha256`. A mismatch aborts the build with the artifact name, URL, expected hash, actual hash, and a hint that the artifact may have been tampered with or that the source registry should be reported.

## Schema evolution

Three independent version numbers coexist in `pylock.ios.toml`. They evolve on different cadences:

| Version | Owner | Bump when |
|---------|-------|-----------|
| `lock-version` | PEP 751 (upstream Python packaging) | Upstream PEP revision. kivy-ios refuses to read major higher than it knows. |
| `[tool.kivy_ios].schema_version` | kivy-ios | Backward-incompatible change to anything under `[tool.kivy_ios]`. Additive changes don't bump. |
| `[tool.kivy_ios].tool_kivy_ios_schema_version` | kivy-ios (echoed from pyproject) | Records the source `[tool.kivy.ios].schema_version` — lets the lock survive `pyproject.toml` iOS schema bumps unambiguously. |

## Worked example: full lockfile for a minimal app

Consider a minimal app: a single source file `src/myapp.py` (with `app_dir = "src"`), depending on `kivy` plus one pure-Python package. The `pyproject.toml` declares `dependencies = ["kivy>=3.0,<4", "more-itertools>=10.5"]` and no `[tool.kivy.ios.native.xcframeworks]` entries (the canonical Kivy case — the kivy wheel ships its own xcframeworks). The user's own `myapp.py` is **not** recorded in the lock — the lockfile pins *dependencies*, not the app's source, which is bundled directly from `app_dir` (see [spec 06](06-xcode-project-generation.md)). The resulting lock looks roughly like:

```toml
lock-version = "1.0"
created-by = "kivy-ios"
requires-python = ">=3.15"
extras = []
dependency-groups = []
default-groups = []

[[packages]]
name = "kivy"
version = "3.0.0"
requires-python = ">=3.10"

[packages.tool.kivy_ios]
direct_requirement = true

# kivy has a compiled C extension, so it ships one wheel per iOS slice. The
# x86_64 simulator slice (ios_13_0_x86_64_iphonesimulator) is also pinned by
# `toolchain lock` but omitted here for brevity; see "Resolution semantics".
[[packages.wheels]]
name = "kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
url = "https://files.pythonhosted.org/packages/<hash>/kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphoneos.whl"
hashes = { sha256 = "..." }

[[packages.wheels]]
name = "kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphonesimulator.whl"
url = "https://files.pythonhosted.org/packages/<hash>/kivy-3.0.0-cp315-cp315-ios_13_0_arm64_iphonesimulator.whl"
hashes = { sha256 = "..." }

[[packages]]
name = "more-itertools"
version = "10.5.0"
requires-python = ">=3.8"

[packages.tool.kivy_ios]
direct_requirement = true

# more-itertools is pure Python, so it has a single platform-agnostic wheel — no
# per-platform entries, and the "Build Python" phase finds no `.so` to convert.
[[packages.wheels]]
name = "more_itertools-10.5.0-py3-none-any.whl"
url = "https://files.pythonhosted.org/packages/<hash>/more_itertools-10.5.0-py3-none-any.whl"
hashes = { sha256 = "..." }

[tool.kivy_ios]
schema_version = 1
toolchain_version = "3.0.0"
generated_at = "2026-05-27T00:00:00Z"
pyproject_sha256 = "e3b0c4..."
tool_kivy_ios_schema_version = 1
[tool.kivy_ios.python_xcframework]
version = "3.15.0"
url = "https://www.python.org/ftp/python/3.15.0/python-3.15.0-iOS-XCframework.tar.gz"
sha256 = "abd43fc362bb6e40a5233a499aa3fa96bf49306ca10b4cbcb27418778e429eb8"

# [[tool.kivy_ios.xcframeworks]] is omitted entirely — this app has no
# user-declared third-party xcframeworks. ANGLE and the SDL3 family ride
# along inside the kivy wheel under `.frameworks/` and are extracted to
# `<app>-ios/Frameworks/` at build time by `toolchain build`.
```

## Artifact-to-project-folder mapping (cross-reference)

This is normative in [spec 03 (artifact distribution)](03-artifact-distribution.md), recapped here:

- `[[packages]]` entries are installed into the generated `<app>-ios/pip-deps/` folder by `toolchain build`. The lock already pins the exact per-slice wheel `url` (or `path`) and SHA-256, so `toolchain build` installs those pinned wheels directly with the right iOS cross-install flags (`pip install --platform ios_... --python-version <X.Y> --abi <abi> --only-binary :all: --no-deps --target <app>-ios/pip-deps`). The `[[packages]]` section is PEP 751-compliant, so it stays readable by any PEP 751-aware tool. The Xcode "Build Python" Run Script phase later converts each `.so` to a per-module `.framework`.
- `[[tool.kivy_ios.xcframeworks]]` entries are downloaded, verified, extracted, and copied into `<app>-ios/Frameworks/`. `toolchain build` registers each in the pbxproj Link Binary With Libraries and Embed Frameworks phases per the `link` / `embed` fields.
